## 1. 结论摘要

| 项目 | 结果 |
| --- | --- |
| 数据源 | `https://dergame.cn`（DerGame · 小Der数据报，自称免费公益工具） |
| 接口 | `POST /api/Items/search` |
| 是否需要登录 | **不需要**。无 Cookie、无 Token、无 UA 校验 |
| 是否需要执行 JS | **不需要**。是纯 JSON API，直接 POST 即可 |
| 返回格式 | `application/json; charset=utf-8` |
| 是否包含我们要的数据 | **是**。真实交易行价格、7 日涨跌、7 日最高/最低、占格尺寸 |
| 单次返回上限 | **100 条**（服务端硬上限，无分页参数） |
| 有效弹药条目 | 见 `data/fixtures/discovery-full-report.json` |
| 价格有效率 | 约 75%（无价格的条目多为不可交易物品） |
| 稳定性评估 | 中。公开免费服务，无 SLA 承诺，随时可能改版或关闭 |

**结论：这条路线可用，可以作为阶段一的主数据源。** 但必须按开发文档第 3 章的设计保留适配器抽象与 fixture 兜底。

### ⚠️ 1.1 第一号陷阱：`name` 不是唯一键

这是本项目最严重的一个坑，实测直接产生了假行情。

数据源里 **`.300BLK` 是三种不同品质的弹药**，共用同一个 `name`，但 ID 与价格完全不同：

| `name` | `id` | `grade` | 价格 |
| --- | --- | --- | --- |
| `.300BLK` | `37280500001` | 5（金） | **4871** |
| `.300BLK` | `37280400001` | 4（紫） | **1604** |
| `.300BLK` | `37280300001` | 3（蓝） | **444** |

如果按 `name` 把它们合并成一个物品，它的"价格"就会在 444~4871 之间漂移 ——
实测产生了 **4871 → 1604（−67%）** 的跳变，被数据质量校验拦住。

**正确的模型**：**一个（`name` + `id`）= 一条独立的价格序列**。
基础表里同名条目必须加品质后缀区分（`300blk_g5` / `300blk_g4` / `300blk_g3`）。

**连带教训**：`slugify` 生成内部 ID 时**必须保留中文字符**。
初版只保留 ASCII，于是 `碳纤维刺骨箭矢` 与 `碳纤维穿甲箭矢` 都被压成 `unknown`
而撞主键 —— 又是两个不同物品共用一条价格序列。

> 检查方法：对数据源做一次 `name` 分组统计，任何 count > 1 的名字都要逐条核对。
> `tools/discover_all_ammo.py` 已实现按 `(name, id)` 拆分，并在写文件前做**主键唯一性自检**
> （不唯一就直接报错退出，而不是产出脏数据）。

## 2. 接口规格

### 2.1 请求

```
POST https://dergame.cn/api/Items/search
Content-Type: application/json
```

请求体支持三种形态（**互斥**，实测得出）：

| 形态 | 示例 | 语义 |
| --- | --- | --- |
| 全量 | `{}` | 返回混合物品（弹药 + 装备 + 配件 + 道具），被 100 条上限截断 |
| 按类型 | `{"type":["弹药"]}` | 只返回该类物品，实测 85 条（**说明弹药总数 > 85，被截断**） |
| 按名称 | `{"name":"5.56"}` | **大小写不敏感的子串匹配**，跨类型返回 |

### 2.2 已确认的参数陷阱

这些是踩过的坑，写代码时必须避开：

| 陷阱 | 现象 | 原因与对策 |
| --- | --- | --- |
| **`grade` 参数会返回空** | `{"grade":["6"]}` → 0 条；`{"grade":[6]}` → 0 条；`{"grade":"6"}` → 0 条 | 服务端不接受该参数。**不要用它过滤，品质在本地筛** |
| **`grade` 与 `type` 同时传会互相污染** | `{"type":["弹药"],"grade":[6]}` → 0 条 | 同上。**一次只用 `type` 或 `name` 之一** |
| **`type` 取值不等于 `primary` 值** | `{"type":["护甲"]}` 实际返回 `primary="装备"` | `type` 是**查询分类名**，`primary` 是**数据字段名**，两者不同名 |
| **`name` 匹配的是物品名，不是口径** | `{"name":"7.62x35mm"}` → 0 条，但存在 5 条该口径弹药 | 见第 3 节，这是最大的坑 |
| **100 条硬上限** | `{}` 与 `{"name":"弹"}` 都恰好返回 100 条 | 必须切片取全，见第 3 节 |

### 2.4 字段语义

| 字段 | 类型 | 语义 | 本项目映射 |
| --- | --- | --- | --- |
| `id` | str | 物品唯一 ID | `ammo.external_ids.dergame` |
| `name` | str | 物品名 | `ammo.name` |
| `grade` | str | 品质 1–6 | `ammo.grade` / `ammo.tier`（1白 2绿 3蓝 4紫 5金 6红） |
| `primary` | str | 实际类型：`弹药` / `装备` / `配件` / `道具` | **过滤键**：只收 `弹药` |
| `second` | str | 口径 / 子类（如 `.357 Magnum`、`弹匣`） | `ammo.caliber` |
| `pic` | str | 图片地址（官方 CDN） | 前端展示用，可选缓存 |
| `length` / `width` | str | 占格尺寸 | `ammo.length` / `ammo.width`，用于算**单格价值** |
| `combat_value` | null | 实测全为 null | 不映射 |
| `dept_value` | int/null | 部门价值 | 暂不映射，预留 |
| **`value.new`** | int/null | **当前价格** | `price_tick.price`（`price_kind='reference'`） |
| **`value.7zf`** | float/int/null | **⚠️ 含义未确认，实测证明它不是涨跌百分比** | 仅原样展示为 `source_index_7zf`；**禁止当作涨跌使用** |
| `value.7df` | float/int/null | 与 `7zf` 配套的另一个指标（含义同样未确认） | 暂不使用 |
| `value.7top` | int/null | **7 日最高价**（实测与自算值一致） | 分位数与回撤计算，同时用于互校 |
| `value.7down` | int/null | **7 日最低价**（实测与自算值一致） | **抄底信号的关键输入** |
| `updateTime` | str | **数据时间**（格式 `YYYY-MM-DD HH:MM:SS`） | 用于新鲜度判断（`stale` 标志） |

#### ⚠️ 关于 `7zf` 的重要更正（这是本项目踩到的一个真实误解）

最初的实测报告把 `7zf` 标注为"7 日涨跌比例（%）"。**这个判断是错的**，由端到端验收的互校环节抓出：

| 物品 | 自算 7 日涨跌 | 数据源 `7zf` | 7 日区间 | 当前价 |
| --- | --- | --- | --- | --- |
| `.357 Magnum FMJ` | −15.85% | **118.45** | 515 – 1125 | 515 |
| `45-70 Govt RN` | −33.59% | **69.26** | 514 – 870 | 514 |
| `.357 Magnum JHP` | −36.42% | **79.13** | 411 – 738 | 412 |

这些物品的价格都**贴近 7 日最低点**，如果 `7zf` 是涨跌幅，绝不可能是 +118% 这种大正数。所以它的定义与涨跌幅不同（可能是某种指数、等级、或与战备值相关的量），**在弄清之前不能使用**。

**正确做法（已实现）**：
- API 字段改名为 `source_index_7zf`，前端标注为"数据源自报指标（定义未知）"；
- 不再与自算涨跌做比对 —— 拿它比对会得出"我们有 bug"的错误结论；
- 改为校验**能真正互校的字段**：数据源自报的 `7top`/`7down` 与自算 7 日高低**完全一致**，
  这证明我们的价格序列、时区处理、历史回补链路都是正确的。

> 这件事本身就是"互校"机制的价值证明：如果只依赖单一来源、不做交叉验证，
> 这个口径误解会一直存在，最终让用户看到一个与事实相反的数字。

### 2.5 字段可信度分级

| 可信度 | 字段 | 依据 |
| --- | --- | --- |
| ✅ 已确认可用 | `id` `name` `grade` `primary` `second` `length` `width` `value.new` | 直接使用，且与自算值一致 |

## 3. 最关键的坑：口径命名不统一（必读）

`name` 参数匹配的是**物品名**，而游戏里的口径写法**极不统一**。实测例子：

| 口径字段 `second` | 实际物品名 `name` | 问题 |
| --- | --- | --- |
| `7.62x35mm` | `.300BLK` | **名字里根本没有这个口径串** |
| `.45-70mm` | `45-70 Govt FMJ` | 名字丢了前导点 |
| `5.56x45mm` | `5.56*45mm M855 APC` | 用 `*` 而不是 `x` |
| `4.6x30mm` | `4.6 x 30mm AP ST` | 加了空格 |
| `5.7x28mm` | `5.7 x 28mm HT+` | 加了空格 |
| `复合弓箭矢` | `玻纤柳叶箭矢` | 完全不同的命名体系 |

**后果**：如果按"完整口径字符串"去切片取数，会**静默漏掉 30+ 条弹药**（包括整个 `.300BLK` 系列和全部箭矢）。

**正解**：用**短数字前缀**做超集匹配，再在本地按 `primary == "弹药"` 过滤。

```
❌ {"type":["弹药"],"name":"7.62x35mm"}   → 0 条（漏掉 .300BLK 全系列）
✅ {"type":["弹药"],"name":"7.62"}        → 覆盖 7.62x39 / 7.62x51 / 7.62x54R / 7.62x35(.300BLK)
✅ {"name":"5.56"}                        → 9 条，含 5.56x45mm 与 5.56*45mm 两种写法
```

`tools/discover_all_ammo.py` 已按此策略实现：**第一轮种子撒网 → 从物品名反推数字前缀 → 第二轮精确切片**。

### 4.1 `chartData` 验证结果（原待验证项 V1/V2 已结案）

**请求**

```
POST /api/Items/chartData
{"itemId": "37220000001", "chartType": 7}
```

| 验证项 | 结果 |
| --- | --- |
| `itemId` 传字符串 | ✅ 成功，返回 8335 字节 |
| `itemId` 传数字 | ✅ **同样成功**（`37220000001` 未丢精度） |
| 结论 | 接口对类型不敏感。**本项目统一传字符串**，避免将来出现精度问题 |

**响应结构**

```json
{
  "name": ".357 Magnum 9号霰射\"鼠弹\"",
  "values": [
    { "time": "2026-10-07 19:00:00", "avg_price": "284" },
    { "time": "2026-10-07 20:00:00", "avg_price": "284" }
  ]
}
```

| 字段 | 语义 | 注意 |
| --- | --- | --- |
| `name` | 物品名 | — |
| `values[].time` | 时间戳，**精确到小时** | 格式 `YYYY-MM-DD HH:MM:SS` |
| `values[].avg_price` | 该小时均价 | **是字符串，不是数字！必须显式转换** |

`chartType`：`7` = 七日图表，`30` = 月度图表（来自站点代码逻辑）。

### 4.2 为什么 `chartData` 价值极高

**它让分位数、回撤、波动率这些分析可以"立即"可用，而不需要等采集攒数据。**

对照开发文档第 12 章的排期：原本 M3 看板做完后，要等 7–30 天才攒够历史用于分位数判断。
现在只要对 85 个可交易条目各拉一次曲线，就立刻拥有 **7 天 × 24 小时的逐小时价格序列**（约 168 个点/条目）。

对应实现调整：

| 原设计 | 调整后 |
| --- | --- |
| 靠自身轮询逐条累积 `price_tick`，几天后才有趋势 | **首次启动即回补 7 天历史**，立刻可用 |
| 分位数需要 7 天样本，期间标注"样本不足" | 启动即有 168 点样本，分区间可用 |
| 历史只能靠自己攒，源失效则历史断裂 | 历史来自数据源，本地库只是缓存与聚合 |

**代价**：83 次额外请求（每个条目一次）。按 1.4 秒间隔约 2 分钟。建议**只在首次初始化或每日一次**执行，不要放进常规轮询。

### 4.3 数据缺口：没有"子弹自选包 / 弹匣"

实测结果的**重要负面发现**：

- 全部 113 条物品的占格尺寸**均为 1×1**（所以单格价值 == 单价，不含包装折算）；
- 物品名中**没有任何含"包"或"匣"的条目**；
- 先前在全量混合响应中观测到的 `second = "弹匣"`（74 条），属于 `primary = 配件/装备`，**不是弹药**。

**结论**：**这个数据源只有散装弹药，没有子弹自选包/弹匣包。**

影响与对策：

1. 开发文档第 6.3 节设计的"包内单发价 vs 散卖单发价"套利分析，**在本数据源上无法直接实现**——因为拿不到"包"的价格。
2. 因此 `ammo_catalog.yaml` 中所有条目 `is_pack: 0`、`pack_size: 1` 是**正确**的，不是遗漏。
3. 若确实需要倒子弹（包→散）分析，有两条路：
   - 手工维护一份"包"的清单（名称 + 含发数），作为 `is_pack: 1` 的条目补充进去；
   - 或接入付费源（三角洲数据帝有"子弹自选包收益"专用接口）。
4. 在实现收益分析时，必须**先检测是否存在 `is_pack=1` 的条目**；没有就如实隐藏该功能，而不是算出一个错误的数字。

## 5. 使用礼仪与风险（务必遵守）

这是一个**个人免费公益服务**，不是商业 API。使用约束：

1. **控制频率**：本项目设计为 60 秒轮询，但**建议实际使用 5–20 分钟一次**。子弹价格变化没那么快，高频轮询只会给对方服务器添负担。
2. **错峰**：加入随机抖动，避免整点集中请求。
3. **本地缓存**：同一次采集周期内不要重复请求同一接口。
4. **标注来源**：如果将来把数据展示给别人看，应标注数据来源为 DerGame。
5. **不要转售数据**：本项目定位是个人自用（见开发文档第 15 章）。
6. **接受它随时消失**：这是免费服务，没有 SLA。适配器抽象与 fixture 兜底是必需品，不是可选项。

### 采集策略建议（基于实测）

| 项目 | 建议值 | 依据 |
| --- | --- | --- |
| 全量快照轮询 | **10–20 分钟** | 弹药共 113 条，一次请求即覆盖；`updateTime` 为分钟级，更快没有收益 |
| 历史曲线回补 | 首次启动 + 每日 1 次 | 83 次请求，约 2 分钟；不要放进常规轮询 |
| 请求间隔 | ≥ 1.3 秒（跑批时） | 礼貌访问，避免被视为滥用 |
| 单次请求规模 | 1 次/轮询（`type=弹药`） | 实测 85 条，未触上限 |
| 失败退避 | 1s → 4s → 16s，连续 3 次告警 | 对应开发文档第 3.5 节 |
